# 元藏文博检索

通过 `yj-museum` MCP 把自然语言或图片线索转成专业检索字段，区分严格匹配与相关扩展，并以可继续操作的藏品列表或详情答复。

## 必须遵循的流程

### 1. 确认 MCP 已接入

先判断当前工具中是否存在服务 `yj-museum` 或工具 `query_coll`、`info_coll`。

- 若可用，继续授权检查。
- 若不可用，运行 `<skill-dir>/scripts/ensure_mcp.py --check`。
- 若脚本报告未配置或地址不正确，立即运行 `--configure`。只修改 `yj-museum` 对应配置，并保留备份。
- 配置发生变化后，告知用户已自动配置 `yj-museum`，请重启 Codex；保留已经拆出的检索计划，重启后继续。不要假装当前会话已经加载新工具。

MCP 地址、工具名和字段以 [MCP 契约](references/mcp-contract.md) 为准。

### 2. 处理首次授权

运行 `<skill-dir>/scripts/yj_museum_client.py auth status`，不要在回复中显示授权码。

- 若已授权，直接继续，绝不再次询问。
- 若未授权，只问一句：“请发送 yj-museum 服务商提供的访问授权码；验证成功后会安全保存在本机，后续不再询问。”
- 收到后，通过标准输入交给 `auth set`。该命令会先调用 `query_coll` 验证，只有成功才保存。
- 授权失败时不要保存，说明授权码无效并请用户重新提供。
- 不把授权码写入 `SKILL.md`、项目文件、Git、普通日志、检索计划或最终答复；不在命令行参数中传递授权码。

凭据助手在 Windows 使用 DPAPI，在 macOS/Linux 优先使用系统凭据存储；系统存储不可用时才退回仅当前用户可读的本地凭据文件。

### 3. 拆解用户意图

先提取用户真正要解决的问题，再拆字段。至少检查：

- 对象与问题类型：查找、识别线索、断代比较、窑口比较、工艺解释、相似器、馆藏分布、查看详情。
- 实体字段：`title`、`creator`、`dynasty`、`kiln`、`material`、`technique`、`glaze`、`motif`、`inscription`、`detailed_form`、`descriptors`。
- 约束与否定：只要、排除、不是、可能、约、仿、款、风格、传、或、至。
- 展示要求：条数、机构、图片、详情、比较维度、是否需要全部结果。

将原话、规范词、相关扩展词分开，不能把推测改写成事实。按 [检索扩展规则](references/query-expansion.md) 选择字段和关联词。

### 4. 处理上传图片

对图片先观察、后推断、再检索：

1. 分别观察整体器形、口沿、腹部、足底、款识或铭文、材质表面、釉色/色彩、装饰技法、纹饰题材、装裱与残损。
2. 把“直接可见”与“推测”分开，并为时代、窑口、工艺、釉色、款识给出高/中/低置信度。
3. 将高置信线索用于严格查询；将中低置信线索作为相关查询，不用于确认身份。
4. 款识不清时只转写能辨认的字，分别查询原字串、规范写法和合理缺字变体。
5. 图片不足时先做最佳努力；只有缺少底部、局部或尺度会实质改变检索时，才建议补拍。

图像相似记录只是馆藏参照，不等于真伪、年代或窑口鉴定结论。

### 5. 生成严格与相关查询

生成一个小而有解释力的查询计划：

- **严格查询**：保留用户明确给出的核心字段，并采用多字段 AND。例如“南宋官窑粉青釉洗”优先使用 `dynasty=南宋`、`kiln=官窑`、`glaze=粉青釉`、`descriptors=洗`。
- **相关查询**：每次只放宽或扩展一个关键维度，保留其他锚点。把同义词、上下位词、跨期馆藏编目和学术争议词放在相关组。
- 不把相邻概念当同义词。例如斗彩不等于五彩，汝窑不等于官窑，“某朝年制款”不等于该朝实物。
- 对“南宋官窑”，严格查 `南宋 + 官窑`；相关补查 `宋 + 官窑`、`宋至元 + 官窑`、`宋元 + 官窑`、`宋金 + 官窑`，并可按问题需要补充“修内司官窑”“郊坛下官窑”“老虎洞窑”。必须标记这些是补充口径，不是严格同义词。
- 无结果时按“规范写法 → 去掉最低置信字段 → 上位词 → 邻近编目词”逐级放宽，记录每一步，禁止一次性删除所有条件。

把计划作为 JSON 交给：

`python <skill-dir>/scripts/yj_museum_client.py batch-search --plan-stdin`

计划格式：

```json
{
  "strict": [{"label": "原始条件", "params": {"dynasty": "南宋", "kiln": "官窑"}}],
  "related": [{"label": "跨期编目：宋至元", "params": {"dynasty": "宋至元", "kiln": "官窑"}}]
}
```

脚本会逐页取回、按 `coll_code` 去重，并把严格结果从相关结果中排除。若结果量超过安全上限导致未完整取回，必须用“至少”而非伪造精确数。

### 6. 排序与研判

按以下优先级排序，不因图片看起来相似就覆盖结构化证据：

1. 用户明确字段完全命中。
2. 名称、时代、作者/窑口、款识等高辨识字段命中。
3. 工艺、釉色、纹饰、器型等组合命中。
4. 仅关键词或视觉相似。

同一藏品被多个查询命中时合并展示，并列出命中理由。对“仿款”“寄托款”“风格”“传”等限定词保留原意。

### 7. 先报数量，再给结果

答复第一句必须是数量结论：

> 严格符合 **N 件**；相关藏品 **M 件**。

若抓取不完整，改为：

> 当前已核实严格符合 **至少 N 件**；相关藏品 **至少 M 件**。

之后按 [输出与交互格式](references/output-format.md) 排版。默认展示前 10 件，不用长段落淹没列表。

每条结果至少包含：名称、时代、作者或窑口（适用时）、工艺/釉色/纹饰（有值时）、收藏机构、`coll_code`、命中理由。字段缺失就写“数据库未提供”，不可补写。

### 8. 支持继续查看

- 用户说“查看 3”“点第 3 件”“查看 `<coll_code>`”时，运行 `detail --coll-code <code>`，再展示完整字段与全部图片链接。
- 用户说“相关藏品”“查相似 3”时，以该条详情中的时代、窑口、材质、工艺、釉色、纹饰和器型生成新计划；不要仅复制标题。
- 用户说“下一页”“更多”时，沿用当前查询与排序，避免重新解释为另一问题。
- 若客户端能渲染 MCP Apps 操作，使用真正的“查看详情/相关藏品”操作；否则用编号与明确回复指令。当前服务没有 UI 资源时，不声称名称可点击。

## 专业边界

- 把数据库记录作为馆藏证据，注明收藏机构、馆藏编号和数据字段；不要把数据库缺失解释为现实中不存在。
- 对学术争议列出不同编目口径和证据，不武断合并。
- 不凭单张图片给出真伪、价格、文物等级、合法流通或所有权结论。
- 用户问博物馆运营、保护、法规等一般行业问题时，先说明 `yj-museum` 是藏品库；仅在馆藏实例能支持回答时调用检索，不把藏品库冒充政策或百科数据库。
- 需要外部最新法规、市场价格或机构动态时，另行使用权威最新来源，并与 MCP 藏品结果分开标注。
